# OpenGrep SAST baseline

Issue #155 pins one static-analysis tool, one rule revision, and one command
so this repository's SAST results are reproducible and reviewed rather than
whatever a contributor's local install happens to find.

## The one command

```
python3 scripts/run-sast.py
```

From a clean checkout this:

1. Downloads the OpenGrep binary pinned in `opengrep.lock.json` for the host
   platform, verifies its SHA-256 against the pinned digest, and verifies its
   `.sig`/`.cert` with `cosign verify-blob` against the pinned Sigstore
   identity (`opengrep/opengrep`'s own GitHub Actions release workflow, via
   keyless OIDC signing -- there is no long-lived public key to pin instead).
   Any mismatch fails closed: `install-opengrep.py` never leaves a
   partially-verified binary at its cache path.
2. Recomputes `rules`' digest over the vendored ruleset in `sast/rules` and
   fails closed if it disagrees with the pinned `rules.digest` -- an
   unreviewed edit to a vendored rule file cannot pass silently.
3. Runs the verified binary against the repository (excluding the paths
   listed in `EXCLUSIONS` inside `scripts/run-sast.py`, each with its own
   rationale), and normalizes the result into a report carrying the tool
   version, rules digest, source revision (`git rev-parse HEAD`), and each
   finding's rule id, path, line range, severity, and message -- never the
   matched source snippet itself, so a report can never carry a copy of
   scanned code.
4. Checks every finding and every scan error against `sast/baseline.json`.
   Exits non-zero, listing exactly what is unresolved, unless every finding
   is a recorded `false_positive` or `hardening` disposition and every scan
   error is an acknowledged `known_errors` entry. A `blocking` disposition
   never passes -- baselining a real defect away would defeat the point of
   classifying it.

`--out PATH` also writes the normalized report as JSON. `--sarif-out PATH`
additionally writes the same findings as SARIF 2.1.0, for issue #156's
upload to GitHub code scanning -- a projection of the same baseline gate,
never a second source of truth: a `false_positive`/`hardening` finding is
carried as a SARIF suppression (with the recorded rationale) rather than
omitted, and a `blocking` or not-yet-classified finding is left
unsuppressed, matching exactly what already fails this command's exit code.
`--binary PATH` skips install/verify and scans with an already-verified
binary (useful for local iteration; CI never uses it). Both runs of the
two-clean-checkouts verification described in issue #155 use the same
command with no flags.

## CI enforcement (issue #156)

`.github/workflows/sast.yml` runs `python3 -B scripts/run-sast.py --out ... --sarif-out ...`
on every pull request and every push to `main` or `rc/*`, with least-privilege
permissions (`contents: read`, plus `security-events: write` solely for the
SARIF upload step) and commit-pinned actions. The job is bounded to 20
minutes (`timeout-minutes`), matching this command's own bounded per-file
`--timeout`. The scan step's real result (`steps.scan.outcome`, which
`continue-on-error` does not mask) is the only enforcement signal: it is
checked in an explicit final "Enforce scan result" step so that the JSON
report, the SARIF report, and the best-effort code-scanning upload all still
run `if: always()` beforehand. GitHub does not apply third-party SARIF
suppressions to alert state during ingestion, so after successful processing
the `main`-branch run invokes the pinned `advanced-security/dismiss-alerts`
action to dismiss reviewed alerts as `won't fix` and re-open action-managed
alerts whose baseline suppression was removed. Pull-request runs never invoke
that repository-wide mutation. Upload and synchronization are both
best-effort: unavailable code scanning, a fork pull request's restricted
token, or an action failure cannot change whether the job passes or fails. A
"Record OpenGrep evidence" step writes the run's source revision, rules digest, tool
version, and finding/error counts to the job summary, which is the exact
run URL and rule digest issue #156 asks to be recorded for issue #145 at
the final release candidate revision.

## Reproducing the initial reviewed baseline

`sast/reports/2026-09-10-initial-baseline.json` is the structured report this
issue's baseline was reviewed against, committed as the historical record;
`sast/baseline.json` is the live disposition ledger `run-sast.py` reads on
every run. Re-running `python3 scripts/run-sast.py` from a clean checkout at
the same source revision reproduces the same `findings` and `errors` arrays
(everything but the `generated_at` timestamp).

## What is excluded, and why

See `EXCLUSIONS` in `scripts/run-sast.py` for the authoritative list; in
summary: build output and lockfiles (`target/`, `node_modules/`, `dist/`,
`build/`, `Cargo.lock`, `package-lock.json`, `pnpm-lock.yaml`) are generated,
not source; `.claude/` is agent-tooling wiring generated by third-party CLIs
(`graft`, `rtk`), not hand-authored application code; `graft/` is its
gitignored local cache; `conformance/fixtures/` holds this project's own
canonical *synthetic* secret-shaped fixtures, and scanning deliberately
secret-shaped text with a generic SAST tool is meaningless and risks a
report copying secret-like values, which this issue's own security
constraint forbids; `docs/coverage/` carries the same synthetic secret-shaped
literals (`detector-inventory.json`'s `reconciliationTrigger` strings and
the files generated from them), excluded for the identical reason;
`sast/rules/` is the vendored third-party ruleset itself, whose embedded
example patterns are not this project's source.

## Rules: vendoring, license, and update procedure

`sast/rules` vendors 141 rule definitions (`.yml`/`.yaml` only, not their
paired `opengrep test` target fixtures) from
[`opengrep/opengrep-rules`](https://github.com/opengrep/opengrep-rules) at
the immutable commit recorded in `opengrep.lock.json`'s `rules.revision`,
covering exactly the surfaces issue #155 asks for:

| path | covers |
| --- | --- |
| `rust/lang/security` | the Rust core and CLI |
| `python/lang/security` | the Python binding and release scripts |
| `javascript/lang/security`, `typescript/lang/security` | the JS/TS package and bindings glue |
| `bash/lang/security`, `bash/curl/security` | shell in release tooling |
| `yaml/github-actions/security` | this repository's own workflows |

**License**: `sast/rules/LICENSE.upstream` is the upstream notice verbatim --
the rules are licensed under LGPL-2.1 with a Commons Clause condition
(no reselling the ruleset itself as a hosted/consulting product). They are
used here purely as a dev-time SAST input: nothing under `sast/rules` is
bundled into a published npm, crates.io, or PyPI artifact (`sast/` is not
part of any package's file list), so the Commons Clause condition never
attaches to anything this project ships.

**Updating the pinned revision**: re-vendor deliberately, never edit a
vendored file in place.

1. Pick a new commit on `opengrep/opengrep-rules`'s `main`; review its diff
   for the paths above.
2. Re-copy just those paths' non-`.test.` `.yml`/`.yaml` files into
   `sast/rules`, replacing what is there.
3. Recompute the digest and update `opengrep.lock.json`:
   `python3 -c "import importlib.util,sys; s=importlib.util.spec_from_file_location('m','scripts/run-sast.py'); m=importlib.util.module_from_spec(s); s.loader.exec_module(m); print(m.compute_rules_digest(__import__('pathlib').Path('sast/rules')))"`
4. Update `rules.revision`, `rules.revision_date`, and `rules.digest` in
   `opengrep.lock.json` in the same change.
5. Run `python3 scripts/run-sast.py`; triage every new finding and error into
   `sast/baseline.json` before merging -- a re-pin that leaves anything
   unclassified fails closed, by design.

**Updating the pinned OpenGrep binary**: pick a release tag, download each
pinned platform's asset plus its `.sig`/`.cert`, verify with `cosign
verify-blob` against `signing.certificate_identity_regexp` /
`signing.oidc_issuer`, record the verified SHA-256, and update
`opengrep_version` and `binaries` in `opengrep.lock.json` together. Never
update the version without re-verifying every pinned asset's signature.

## Finding and error dispositions

`sast/baseline.json` has two sections:

- `findings`, keyed by a stable id (`sha256(rule_id|path|start_line|end_line)`,
  truncated). Each entry needs `classification` (`blocking`,
  `false_positive`, or `hardening`) and a `rationale` explaining which, so a
  future reviewer can judge whether it still applies rather than trusting an
  unexplained baseline entry.
- `known_errors`, keyed the same way over `(type|path|line)`, for scan errors
  (a broken/unsupported rule, a rule or file timeout, a parse failure) that
  are acknowledged tool/rule limitations rather than defects in this
  repository -- see the two limitations already recorded there:
  `PartialParsing` from OpenGrep 1.30.0's TypeScript parser rejecting
  `unique symbol`, and from the vendored `curl-eval` rule's Bash sub-parser
  choking on GitHub Actions' `${{ ... }}` expression syntax.

A `blocking` finding must be fixed in application code, not dispositioned
away. Everything else in this baseline was reviewed and is a narrow,
justified `false_positive` (each entry's `rationale` says exactly why the
matched code is not exploitable the way the rule assumes) with the sole
`hardening`-eligible category unused so far -- there is currently no accepted
non-blocking improvement in the initial baseline.
