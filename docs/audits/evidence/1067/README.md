(new matrix families, PII in the matrix, finding-type keys) belongs in
`redact-secret/redact-secret-benchmarks`, and no vendored file under

Reading the table:

- A detector is counted once, at the weakest status among the families that
  list it. The matrix is keyed by detector id, and the harness scores 25 finding
  types of 15 shipped detectors as their own arrival families under ids the
  inventory does not have (`slack-app-level-token`, `vercel-personal-access-token`,
  and so on). The reviewed allowlist names each owner, and the report attributes
  those families to the owner, so a weaker folded family is not hidden behind its
  detector's stable ones. Without that attribution `slack-token` would read as
  stable although `slack:app-level-token` is provisional.
- The 144 stable families are matrix families, not detectors: 102 detectors back
  them. "144 stable" is not "144 detectors".
- The 21 matrix families without a detector are measured *absences* (the
  matrix says why, for example `vercel:api-key`, pending, no reviewed grammar).
  They are not shipped detections and need no core work.
- Detector-level join is the finest grain the matrix allows. It carries no
  finding-type key, so 16 multi-type detectors cannot be checked type by type.
  `generic-token`, for example, emits `authorization_credential`,
  `contextual_secret` and `vendor_prefixed_credential` under the single family
  `generic:unclassified-assignment-literal`.

## Shipped but unmeasured, and the proposed disposition

### Credential detectors: none

`python3 -B scripts/check-detector-family-coverage.py --strict` passes and its
allowlist `unmeasured` set is empty, so no shipped credential detector is
silently absent from the matrix. Eight detectors are measured but not stable:

| Detector | Matrix family and status | Why (matrix `reason`, abridged) | Owner of the next step |
| --- | --- | --- | --- |
| `bearer-token` | `generic:bearer-token`, provisional | protected holdout not run, needs a frozen candidate | benchmarks, at freeze |
| `connection-string` | `generic:connection-string-password`, provisional | same | benchmarks, at freeze |
| `otpauth-uri` | `generic:otp-seed`, provisional | same | benchmarks, at freeze |
| `generic-token` | `generic:unclassified-assignment-literal`, provisional | exact-span 1 and leaked-span 1 where 0 is required; holdout not run | core (the miss) then benchmarks |
| `okta-api-token` | `okta:api-token`, provisional | 4 unresolved contradictions among sources | benchmarks (research) |
| `slack-token` (folded id `slack-app-level-token`) | `slack:app-level-token`, provisional | 0 of 3 required dated references | benchmarks (research) |

Proposed disposition: leave each at its measured status. None needs the
"excluded from the stable support claim" wording because each already carries a

`generic-token` miss matter most for the contract: they describe Beta.12 code,
and `generic_token.rs`, `connection_string.rs`, `otpauth.rs` and
`bearer_token.rs` changed afterwards.

## Defects found

1. **PII statuses are unbound and ungated.** Six shipped families have no row in
   the support matrix; their statuses live in prose that cites a candidate
   (`8b6a5fde`) two releases behind, and no check ties the prose to the shipped
   families or revisions.
2. **The public count has no denominator.** 144/7/5/17 describe 173 matrix
   families (21 of which are not shipped detections); nothing states that 110
   detectors ship or that all of them map.
3. **The measured candidate is not the source under review.** 27 detector files
   changed after `4227160c`, including the code behind the four provisional
   `generic:*` families whose gating item is a protected holdout "requires pass
   on frozen candidate".
4. **No finding-type key in the matrix**, so 16 multi-type detectors cannot be
   checked per finding type. This is a limit, not an observed gap.
5. Three different benchmarks revisions are vendored (table above); only one
   produced the statuses.

Not defects: the empty `unmeasured` allowlist and the 25 allowlisted folded ids
are consistent with the matrix and the inventory (the strict check passes).

## Decisions needed from the owner

1. Which benchmarks revision is "the pinned benchmarks revision" in public
   counts? Recommendation: `sourceReport.revision` of the matrix (`e8f73bfd` now),
   because it produced the statuses; keep `pin-source.json` as pin hygiene.
2. Should PII statuses move into the pinned matrix (benchmarks work) before the
   v0.1.0 freeze, or stay hand-written and be bound by a new check here?
   Recommendation: matrix, with this repository's generator emitting the
   detection reference table, because that removes the drift class rather than
   guarding it.
3. May `scripts/generate-support-matrix-docs.py` append the denominator and
   identity sentence proposed above to the generated README block and
   `docs/support-matrix.md` (changes two generated files)? Recommendation: yes.
4. Is the Beta.12 candidate's `generic:*` provisional status acceptable to carry
   into the v0.1.0 contract as "provisional on a frozen candidate pending the
   protected holdout", or must those four reach stable first? Recommendation:
   carry them as provisional with the reason; do not delay for them.
5. Approve renaming "Independent tool/community corroboration" in
   `redact-secret/redact-secret-benchmarks`.

## Implementation

Core-side work for [#1186](https://github.com/redact-secret/redact-secret/issues/1186)
and [#1187](https://github.com/redact-secret/redact-secret/issues/1187), after
the owner accepted the recommendations in "Decisions needed" above.

### PII statuses gated and bound (#1186)

- `scripts/check-pii-family-status.py` (tests:
  `scripts/tests/test_check_pii_family_status.py`, run by
  `npm run pii-family-status:check`, wired into `check:docs` and `ci`). It
  fails when a shipped PII family (`const FAMILY_ID` under
  `crates/secret-scan-core/src`) has no row in
  `docs/coverage/pii-family-status.json` or in the Opt-in PII table of
  `docs/reference/detection.md`; when either names a family that does not ship;
  when the documented status differs from the binding or is not
  `pending`/`provisional`/`stable`; when the pinned matrix already carries a
  `pii:` family with a different status; when a recorded revision is not a full
  40-hex id or is absent from the page; and when a PII source file changed
  since the qualification is missing or not named on the page.
- `docs/coverage/pii-family-status.json` binds the six statuses to core
  `8b6a5fde52ecb4dfce13f09c7a947062d21483c7` (`0.1.0-beta.11`) and benchmarks
  revision `be0fb9f35045bf05e5b999a2c0ed368541f9e963`, and lists the PII files
  that changed after that core revision: `pii.rs`, `pii_email.rs`,
  `pii_iban.rs`, `pii_payment_card.rs`, `pii_phone.rs`, `pii_us_ssn.rs`
  (6 production files plus a new test file, +1693/-91 lines in all). The issue
  named email, IBAN and phone; payment-card, SSN and the shared adapter changed
  too, and the page now says so.
- `docs/reference/detection.md` states the two revisions and that the statuses
  were measured on earlier code and not re-measured. The report script prints
  the same binding. When
  [`redact-secret/redact-secret-benchmarks#647`](https://github.com/redact-secret/redact-secret-benchmarks/issues/647)
  puts the families in the pinned matrix, the gate already requires the matrix
  and the binding to agree; retire the table and binding then (not done here,
  there is nothing to read yet).

### Generic family recheck on current main (#1187)

Scope: the four provisional `generic:*` families. Method: the public
conformance corpus `conformance/fixtures/synchronous-corpus.json` (synthetic,
exact start/end offsets, detector and finding type per fixture), asserted
byte-exact against the current registry by `canonical_corpus`,
`common_profile_corpus` and `detectors_conformance` (all pass on this branch;
`cargo test -p redact-secret --lib` 1838 passed). No protected material was
read, and the matrix does not name the case behind its recorded miss
(`policyQualification` carries counts only), so that case cannot be rebuilt
from public data.

| Family (detector) | Matrix, Beta.12 | Public fixtures on current main | Reproduced? |
| --- | --- | --- | --- |
| `generic:unclassified-assignment-literal` (`generic-token`) | exact-span miss 1, leaked span 1 of 76 positives; holdout not run | 288 fixtures (120 positive, 151 negative, 8 boundary, 5 overlap, 4 adversarial), all exact; 5 are declared `intentionally-unsupported` non-detections | **No** from public fixtures; the recorded case is unidentifiable, so its absence is not shown |
| `generic:bearer-token` (`bearer-token`) | 0 misses of 16; holdout not run | 58 fixtures, all exact | No |
| `generic:connection-string-password` (`connection-string`) | 0 misses of 32; holdout not run | 108 fixtures, all exact | No |
| `generic:otp-seed` (`otpauth-uri`) | 0 misses of 9; holdout not run | 31 fixtures, all exact | No |

Result: no family reproduces a miss from public fixtures, so no detector change
was made and no regression case was added. The one recorded miss
(`generic-token`) is neither reproduced nor shown absent, so all four families
stay `provisional` with the matrix's reason (protected holdout not run on a
frozen candidate; the measured build predates later changes to
`generic_token.rs`, `connection_string.rs`, `otpauth.rs`, `bearer_token.rs`).
The contract page says this. Settling it needs the benchmarks policy run on the
freeze candidate to name the case; that is
`redact-secret/redact-secret-benchmarks` work.

## Regenerate

```sh
python3 -B scripts/report-detection-support.py --source-revision "$(git rev-parse HEAD)"
python3 -B scripts/report-detection-support.py --json   # machine-readable
python3 -B scripts/check-detector-family-coverage.py --strict
```

The report is offline and deterministic (no network, no timestamps). It is a
report, not a gate: the gate is `check-detector-family-coverage.py --strict`.
The tracked copy [`detector-support-join.md`](detector-support-join.md) is the
frozen output for the revision above; regenerate it, do not edit it, when the
matrix or the candidate changes.
