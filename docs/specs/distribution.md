# Distribution

Rules governing what ships, in what shape, from which registry, and under what identity.

> Generated for [issue #597](https://github.com/redact-secret/redact-secret/issues/597) (DS6a). Each rule
> below states current behavior in the present tense and links the ADR
> (`docs/decisions/`) that decided it. An ADR records why and when; this file
> records what is true now. Per
> [`decision-decide-artifact-taxonomy-spec-routing-and-evidence-placement`](../decisions/2026-09-22-decide-artifact-taxonomy-spec-routing-and-evidence-placement.md),
> a decision that applies an existing policy to one more provider family or
> one more instance is a row here plus its supporting evidence, not a new
> ADR.

## Rules

| Rule | Governing ADR |
| --- | --- |
| Every published binding (core, wasm, node-native, CLI) ships the same version number from the same release, never independently. | [Release bindings in lockstep](../decisions/2026-09-09-release-bindings-in-lockstep.md) |
| Every registry, import, binary, and internal metadata namespace uses the `Redact Secret` / `redact-secret` identity: repository `redact-secret/redact-secret`; npm `@redact-secret/core`, `@redact-secret/wasm`, `@redact-secret/node-<platform>`; crates `redact-secret` and `redact-secret-cli`; Rust import `redact_secret`; CLI binary `redact-secret`; PyPI `redact-secret`, Python import `redact_secret`. Exported error type names (`SecretScanError`, `SecretScanErrorCode`) and the `crates/secret-scan-core` and `crates/secret-scan-cli` directory paths are explicitly excluded. | [Adopt the Redact Secret naming contract](../decisions/2026-09-10-adopt-redact-secret-naming-contract.md) |
| Workspace identity metadata lives in `Cargo.toml`'s `[workspace.metadata.redact-secret]` table, and manifest `repository`/`homepage`/`bugs` URLs point at `redact-secret/redact-secret` (transfer completed by #157). | [Adopt the Redact Secret naming contract](../decisions/2026-09-10-adopt-redact-secret-naming-contract.md) |
| `scripts/check-legacy-identifiers.py` fails `npm run ci` on any old-identity hit outside its exact-path, rationale-bearing historical allowlist; historical ADRs, closed audits, and the Python-repository redirect are allowlisted, current documentation, manifests, and code are not. | [Adopt the Redact Secret naming contract](../decisions/2026-09-10-adopt-redact-secret-naming-contract.md) |
| The host-integration packages from the separate adapters repository use `@redact-secret/adapter*` (npm) and `redact-secret-adapters` (PyPI). "Adapter" has three distinct meanings that are not renamed: *stream adapters* (the `Transform`/`TransformStream` wrappers in `packages/javascript/src/adapters/`), *host adapters* (the CLI and language bindings over the one core), and these *host-integration packages*. | [Adopt the Redact Secret naming contract](../decisions/2026-09-10-adopt-redact-secret-naming-contract.md) |
| A release ships its full artifact set together, never a partial subset: crates.io `redact-secret` then `redact-secret-cli` (`publish-crates`, core before CLI); PyPI `redact-secret`, the qualified abi3 wheels plus source distribution (`publish-pypi`); npm `@redact-secret/core` from `packages/javascript` (`publish`), after its runtime dependencies -- the per-platform `@redact-secret/node-<platform>` packages (`publish-native-dependencies`) and `@redact-secret/wasm` (`publish-wasm-dependency`) -- all in one idempotent `release.yml` graph. | [Ship the first release's full artifact set](../decisions/2026-09-10-ship-first-release-artifact-set.md) |
| The root npm package is private tooling and the binding Cargo crates are private; their generated npm and PyPI artifacts are the public product. Every version-bearing manifest, the private root included, is held in lockstep. | [Ship the first release's full artifact set](../decisions/2026-09-10-ship-first-release-artifact-set.md) |
| npm publishes all eight `node-publish-targets` Node addons: the six glibc, macOS, and Windows triples plus `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`. On Linux the loader selects the `gnu` or `musl` package by the detected host libc (`process.report` `glibcVersionRuntime`), never by trying one and falling back, because a wrong-libc addon fails process-fatally rather than as a catchable error. | [Ship the first release's full artifact set](../decisions/2026-09-10-ship-first-release-artifact-set.md) |
| The CLI ships the six non-musl `cli-release-targets`; no static musl CLI binary is published. `docs/qualification.md` owns the exact Node, Python, browser, and platform target lists. | [Ship the first release's full artifact set](../decisions/2026-09-10-ship-first-release-artifact-set.md) |
| Node consumers fall back to the WebAssembly build when the native addon is unusable for their platform. | [Add a Node WebAssembly fallback when the native addon is unusable](../decisions/2026-09-19-add-node-webassembly-fallback.md) |
| Logging and tracing host-integration adapters (`@redact-secret/adapter*` / `redact-secret-adapters`) ship from the separate `redact-secret/redact-secret-adapters` repository, not this one. | [Graduate logging and tracing adapters to a separate repository](../decisions/2026-09-19-graduate-adapters-to-a-separate-repository.md) |
| `@redact-secret/core` is verified against Cloudflare Workers and Vercel Edge before those runtimes are claimed as supported. | [Verify @redact-secret/core on Cloudflare Workers and Vercel Edge](../decisions/2026-09-19-verify-edge-runtimes.md) |
| AI-context integrations implement the framework-neutral boundary contract in `docs/reference/ai-context-boundary.md`: four operations, `ok`/`blocked`/`aborted` outcomes with a fixed reason set, allowlisted safe finding metadata, staged single-use streams, and fail-closed traversal, pinned by `conformance/fixtures/ai-context-boundary.json` and replayed against every publish-shaped JavaScript lane and Python wheel. The AI-context adapter alone may depend on the whole-input `policy`/`limits` options, the incremental session, `SecretScanError.code`, and the full safe finding field set; the logging and tracing adapters keep the four-item surface. | [Define the framework-neutral AI-context boundary contract](../decisions/2026-09-25-define-the-framework-neutral-ai-context-boundary-contract.md); [Redact key-identified leaves in place, make `resources/read` the next MCP boundary, and defer Python MCP](../decisions/2026-09-25-rule-on-the-mcp-boundary-open-questions.md) and [Scan a structured leaf with its immediate key through a key-context view](../decisions/2026-09-25-define-key-aware-sanitize-value.md) (beta.10 and later; not yet in force) |
| An official MCP integration implements `docs/reference/mcp-boundary.md`, a thin specialization of the AI-context contract that adds no scan, walk, policy, or error mapping: the whole `CallToolResult` is one bounded `sanitizeValue` (text scanned as text, `_meta` and every field included, limits from the result root); `image`/`audio` `data` and `resource.blob` block as `unsupported_value` unless the host opts in to pass them unscanned, and an unknown block type blocks; the sanitized value-shaped parts are serialized and rescanned, and a `redact`/`block` finding there blocks as `policy`; opt-in argument sanitation uses the `tool-arguments` label; a streamed result stops pulling and closes its producer when the stream's input-free `accepting` turns `false`; every `blocked` outcome maps to one fixed `isError` `CallToolResult`, a tool or producer failure to a second (`tool_error`, error never read), `aborted` to no response, never a JSON-RPC error; audit is `onFinding` plus `{ stage, outcome, reason?, code? }`. The authoritative boundary is in the MCP host before logging, persistence, or model context. Supported, and tested by the adapter at both endpoints: `@modelcontextprotocol/sdk` `>=1.13.0 <=1.30.1`, `@modelcontextprotocol/client`/`server` `>=2.0.0 <=2.1.0`, protocol revisions 2025-06-18 and 2025-11-25, stdio and Streamable HTTP, Node.js 20/22/24; the Python `mcp` SDK is not supported. Pinned by `conformance/fixtures/mcp-boundary.json`, replayed against every publish-shaped JavaScript lane. Widening the range is an edit of this row backed by the adapter's compatibility evidence. | [Define the supported MCP redaction boundary](../decisions/2026-09-25-define-the-supported-mcp-redaction-boundary.md); [Redact key-identified leaves in place, make `resources/read` the next MCP boundary, and defer Python MCP](../decisions/2026-09-25-rule-on-the-mcp-boundary-open-questions.md) and [Scan a structured leaf with its immediate key through a key-context view](../decisions/2026-09-25-define-key-aware-sanitize-value.md) (beta.10 and later; not yet in force) |
| An official MCP integration that claims `resources/read` implements `docs/reference/mcp-resources-read.md`, a thin specialization of the MCP and AI-context contracts that adds no scan, walk, or policy: the whole `ReadResourceResult` is one bounded key-aware `sanitizeValue` under the `resource` label (every `contents[]` entry's `uri`, `mimeType`, `text`, and `_meta`, the result's `_meta`, and every other field; limits from the result root), `text` scanned as text whatever its `mimeType`, then the same key-context backstop; an entry is exactly one of a string `text` or a `blob`, and a `blob` blocks as `unsupported_value` unless the host opts in with the tool-result `binaryContent: "pass"`; every `blocked` outcome maps to the fixed JSON-RPC error `-32603` with a fixed input-free message and no `data`, a read that throws or rejects to `read_error` (same code, a second fixed message, error never read), and `aborted` to no response; audit is `onFinding` plus `{ stage: "resource", outcome, reason?, code? }`. The authoritative boundary is in the MCP host before logging, persistence, or model context. `resources/list`, `resources/templates/list`, `resources/subscribe` and its update notifications, and every other message stay excluded. Supported range: the MCP row's, tested by the adapter at both endpoints of each line on stdio and Streamable HTTP. Pinned by `conformance/fixtures/mcp-resources-read.json`, replayed against every publish-shaped JavaScript lane. | [Define the supported MCP `resources/read` boundary](../decisions/2026-09-25-define-the-supported-mcp-resources-read-boundary.md) |
| The logging, tracing, and AI-context reference architectures (`examples/logging-redaction`, `examples/tracing-masking`, `examples/ai-context`; index `docs/guides/reference-architectures.md`) consume the adapters as a downstream user would: released `@redact-secret/adapter*` and `@redact-secret/core` from the npm registry at exact versions pinned by a committed `package-lock.json` (the AI-context reference takes its adapters from the `examples/mcp-redact` golden path's lockfile). No example, reference, or qualification job consumes an unreleased adapter: the adapters tarball pin (`adapters/pin-source.json`) was retired once adapters train 2026.09.25 published every package it pinned, and a pre-release adapter is tested in `redact-secret-adapters`, not here. The `golden-path` qualification job installs the candidate core with the golden path's locked registry adapters, verified against the lockfile's integrity. The locked registry versions (`adapter-ai-context@0.1.0-alpha.1`, `adapter-mcp@0.1.0-alpha.1`, `adapter@0.1.2`) include the key-aware `sanitizeValue` and `resources/read` rows above; the AI-context smoke demonstrates both at the authoritative host placement. They carry no copy of adapter code. Each has one smoke command (`npm run reference:logging`, `reference:tracing`, `reference:ai-context`) that runs the real core, checks every destination for its synthetic values before printing anything, and runs in the `reference-architectures` CI job. | [Graduate logging and tracing adapters to a separate repository](../decisions/2026-09-19-graduate-adapters-to-a-separate-repository.md) |
